# Локальная разработка

## Требования

Подготовка выполняется в `C:\Users\user\PycharmProjects\LedgerFlow_FinTech` на Windows 11. Проверены Node.js `24.11.1`, npm `11.6.2`, Python `3.14.3`, Git `2.52.0.windows.1`, Docker client/server `29.0.1`, Docker Compose `2.40.3-desktop.1`, GitHub CLI `2.105.0` и Codex CLI `0.172.0`.

Node.js сейчас обслуживает только инструменты QA. Наличие Python и Docker не означает выбора продуктового backend или базы данных. Решение будет принято после полного ТЗ.

## Установка и проверки

Из корня репозитория:

```powershell
npm ci
npm run browser:install
npm run preflight
npm run check
npm run test:e2e
npm run check:evidence
```

`npm ci` использует зафиксированный lockfile. `npm run browser:install` устанавливает Chromium в проектную `.cache/ms-playwright/`, исключённую из Git; Playwright npm-команды используют тот же путь через `scripts/playwright.mjs`. Для Linux CI браузер и системные библиотеки устанавливаются командой `npm run browser:install -- --with-deps`. Preflight проверяет окружение; статические проверки не заменяют продуктовые тесты.

GitHub CLI отсутствует в PATH текущего процесса. Для прямого вызова используйте проверенный путь без изменения глобального PATH:

```powershell
& 'C:\Program Files\GitHub CLI\gh.exe' --version
```

Не сохраняйте токены или полный вывод окружения в документации и отчётах.

## Видимое браузерное тестирование

```powershell
npm run test:e2e:headed
npm run check:evidence -- headed
```

Запускается видимый Chromium с одним worker и замедлением действий 600 мс по умолчанию. Значение можно переопределить переменной `LEDGERFLOW_SLOW_MO` в диапазоне 0–5000 мс. Конфигурация сохраняет доказательства отдельно для двух режимов:

- `artifacts/playwright/headed/` — видимые запуски;
- `artifacts/playwright/headless/` — фоновые запуски;
- внутри каждого режима: `test-results/` со скриншотами, видео и trace, `html-report/` и `results.json`.

Папка `artifacts/` исключена из Git. Результаты конкретного запуска фиксируются в `PROGRESS.md`.

`check:evidence` проверяет фактическое наличие непустых записей и принадлежность всех вложений каталогу выбранного режима. Это защищает от смешивания headed/headless записей при повторной загрузке конфигурации в Playwright workers.

Стенд из `tests/fixtures/` является QA-образцом для проверки браузерной инфраструктуры. По нему нельзя делать вывод о готовности финансовых операций или Chaos Lab.

Отдельный запуск стенда:

```powershell
npm run qa:serve
```

Откройте локальный адрес, напечатанный сервером. Сервер привязан к `127.0.0.1`. Остановите его `Ctrl+C` в том же терминале. Playwright самостоятельно запускает и останавливает свой тестовый сервер.

Просмотр последнего HTML-отчёта:

```powershell
npm run test:report
```

Эта команда открывает headed-отчёт. Для headless-отчёта используйте `node scripts/playwright.mjs show-report artifacts/playwright/headless/html-report --host 127.0.0.1`.

Управление режимами, видео и trace сверяется с [Playwright Configuration](https://playwright.dev/docs/test-configuration), [Videos](https://playwright.dev/docs/videos) и [Trace viewer](https://playwright.dev/docs/trace-viewer). Артефакты содержат снимки проверяемого интерфейса: используйте синтетические данные.

## Git и завершение блока

Рабочая ветка — `feat/ledgerflow-build`. Главный агент проверяет diff и результаты, обновляет документацию, затем создаёт Conventional Commit и push. Не добавляйте `.idea/`, `node_modules/`, секреты, локальные базы и `artifacts/`.

CI-конфигурация находится в `.github/workflows/bootstrap.yml`; наличие workflow не доказывает успешный запуск. Статус проверяйте на GitHub после push и записывайте фактический результат. Force push и автоматический merge в `main` запрещены.

## Диагностика

- Если Chromium отсутствует, повторите `npm run browser:install` из корня проекта.
- Стенд и Playwright используют фиксированный порт `4173`. Если он занят, определите владеющий им процесс; не завершайте чужие процессы или контейнеры. Остановите собственный экземпляр стенда перед тестами. Перенос порта потребует согласованного изменения сервера и Playwright-конфигурации.
- Если Docker недоступен, проверьте Docker Desktop и Engine. Продуктовые контейнеры на этапе подготовки не создаются.
- При ошибке проверки сохраните команду, код завершения и воспроизведение; исправьте причину и повторите затронутую проверку.
